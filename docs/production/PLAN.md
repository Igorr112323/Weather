# План доведения AgroCast до production-уровня

Дата плана: **2026-09-05**, обновлён **2026-09-06** (добавлен контур D — десктоп-приложение по решению владельца; исполнение идёт по разделам).

[Аудит и доказательства](AUDIT.md) · [Чек-лист выпуска](RELEASE_CHECKLIST.md) · [Десктоп-контур](DESKTOP.md)

## 1. Цель и границы

Сделать из существующего MVP **безопасный, воспроизводимый и обслуживаемый сервис агропрогноза**, а не переписать проект и не увеличить число моделей.

Базовое допущение плана — сетевой сервис для нескольких пользователей с сохранёнными отчётами. Первый этап — закрытый пилот: **кукуруза на зерно, явно разрешённые точки Краснодарского края, только проверенные режимы и горизонты**. Ростов, Ставрополь и произвольные точки России не объявляются production-ready автоматически из-за наличия кнопки или JSON-сетки.

Если продукт останется исключительно локальным однопользовательским приложением, PostgreSQL и часть управления доступом можно упростить. Исправления временной валидации, единиц измерения, свежести и сохранности данных всё равно обязательны.

### Неизменяемое правило работы с кодом

**Новый и изменяемый код — строго без комментариев.** Не добавлять поясняющие docstring, inline-комментарии, `noqa`, `type: ignore`, JS/HTML/CSS-комментарии. Объяснения, формулы, ограничения и архитектурные решения размещать в Markdown; смысл кода выражать именами, типами, небольшими функциями и тестами. Не обходить проверки комментариями-исключениями. Массовое переписывание старых файлов ради форматирования не смешивать с исправлением поведения.

## 1.1. Эксплуатационная модель (решение владельца от 2026-09-07)

Продукт распространяется как приложение на одном компьютере пользователя: скачал приложение —
расчёты идут на этом же компьютере, данные скачиваются на него же. Следствия для backlog:

- «продакшен» означает надёжный локальный цикл: атомарная публикация наборов данных (T14),
  устойчивое скачивание источников (T13-локальный контур), целостный кэш результатов,
  работоспособные сборки трёх ОС и понятный откат — а не облачное масштабирование;
- веб-контур остаётся в режиме пилота со своими научными и release-гейтами и не ослабляется;
- очереди/реплики/балансировка (G02-облачная часть) не блокируют локальный релиз, но и
  не объявляются готовыми;
- крупные данные не коммитятся в Git: доставка — сборка приложения с seed-bundle плюс
  публикация обновлённых bundle release-ов в каталог машины (механизм — T14, CLI — T13).

## 2. Приоритеты и условия остановки

- **P0:** блокирует публичный выпуск затронутой функции. Исправить либо исключить функцию из релиза с проверяемым запретом на уровне API.
- **P1:** требуется до стабильной промышленной эксплуатации, даже если закрытый пилот временно допускает ограничение.
- **P2:** оптимизация/расширение после измеренного спроса и прохождения release gates.

Нельзя «починить» аудит снижением порогов под новые результаты, скрыть устаревшие данные увеличением TTL или назвать fallback полноценным прогнозом. При ухудшении честно пересчитанного навыка публикуется новый результат и сужается допустимый scope. Коммерческие обещания не являются критерием выбора метрик.

## 3. Целевая архитектура без лишнего усложнения

Оставить Python, FastAPI, численное ядро, Leaflet и модульную структуру. Разделить процессы и источники состояния:

| Компонент | Ответственность |
|---|---|
| Caddy | TLS, безопасные заголовки, ограничение размера запроса, внешний доступ |
| FastAPI | Аутентификация, авторизация, валидация, постановка задач, чтение статусов/отчётов |
| Worker из того же codebase/image | Ограниченные CPU-задачи; без обучения или скачивания многолетних данных внутри HTTP-обработчика |
| PostgreSQL | Пользователи/владение, справочник, подписки, задачи, выпуски, оценки; миграции и транзакции |
| Redis + RQ | Доставка и ограничение фоновых задач; не единственное хранилище результата |
| Версионируемое файловое/object storage | Неизменяемые снимки Zarr/Parquet и model bundles с manifest и checksums |
| Один scheduler/ingest worker | Обновление источников, построение признаков, обучение, оценка и продвижение согласованного release |

Очередь работает с устойчивым `job_id`; состояние и outbox фиксируются транзакционно. Повторная доставка задачи допустима, повторная публикация одного результата — нет. Redis можно восстановить из ожидающих записей БД. Для пилота допустим local versioned volume с внешним backup вместо немедленного внедрения S3.

`AGROCAST_WORLD_DIR` означает выбранный bundle для чтения; `AGROCAST_STATE_DIR` — runtime-кэш/рабочее хранилище. Старые `AGROCAST_WORLD` и `AGROCAST_DATA` — только совместимые aliases без конфликтующих значений. Запись пользовательских данных в слой Docker-образа исключается. Альтернативный `serve/api.py` нужно объединить с основным API либо явно вывести из поддерживаемого production entrypoint.

## 4. Этапы

Роли: **BE** — backend/reliability, **ML** — данные и валидация, **FE** — интерфейс, **Ops** — инфраструктура, **QA** — проверки, **PO** — владелец продукта; агроном и специалист по правам подключаются к соответствующим gates.

Оценка при двух основных инженерах BE/ML и частичном участии FE/QA/Ops: **ориентировочно 10–14 недель**, с пересмотром после временного аудита T08. Это плановый диапазон, не обещание. Новая независимая forward-история может потребовать дополнительных месяцев/сезонов; её нельзя получить ускорением вычислений.

| Этап | Ориентир | Главные работы | Выходной gate |
|---|---|---|---|
| 0. Ограничить риск | Первые 2–3 дня | T01, временное ограничение доступа, фиксация baseline | Только контролируемое окружение; нет открытых mutations/вычислений и безусловных обещаний навыка |
| 1. Безопасный и устойчивый каркас | Недели 1–3 | T02–T07, начало T17/T18 | Негативные HTTP-тесты, ограничения очереди, restart-safe статусы, сохранность состояния и fail-closed readiness |
| 2. Исправить научный контракт | Недели 2–7 | T08–T12, T14, T16 | Строгий as-of, единый pipeline, локальные факты, корректные метрики и разрешённый набор агрорекомендаций |
| 3. Наладить выпуск и обслуживание | Недели 5–10 | T13–T15, T17–T23 | Версионируемые данные/модели, CI/CD, мониторинг, restore/rollback, проверенный UI и права на данные |
| 4. Пилот и решение о релизе | Недели 11–14 | T24 и закрытие оставшихся gates | Не менее 14 дней наблюдаемого пилота и подписанный go/no-go |

Если исследовательские gates не пройдены, этап 4 выпускает только честно ограниченный экспериментальный сервис/климатологию, а не сервис с заявленным подтверждённым прогнозным навыком.

#### T06 · P0 · Устойчивая очередь и ограничение вычислений

**Владелец:** BE · **Размер:** XL · **Риски:** R01, R04, R05 · **Зависимости:** T04, T05.

Заменить `JOBS`/daemon threads на persistent state machine: queued/running/succeeded/failed/cancelled, outbox, lease/heartbeat, retry с backoff, deadline, идемпотентная публикация. Ввести quotas, deduplication, retention; concurrency ограничить глобально, включая region subjobs и BLAS threads.

**Приёмка:** API и worker можно перезапустить посреди задачи без потери её идентичности; две API-реплики возвращают один статус; повторная доставка не дублирует выпуск; переполнение даёт 429/503 с retry policy, а не новый поток; отмена освобождает ресурсы и не оставляет дочерних процессов.

**Статус:** реализован и локально проверен на PostgreSQL (pgserver) и SQLite: [очередь, песочница и runbook](QUEUE.md), [точные прогоны](PROGRESS.md). Приём закрыт флагом `AGROCAST_QUEUE_INTAKE=false` и отдельным научным gate'ом — инфраструктура не включает расчёты. Docker compose-сервис `worker` декларирован, но фактический container rollout не выполнялся (нет Docker в среде проверки).

#### T07 · P0 · Readiness и явная свежесть входов

**Владелец:** BE + ML · **Размер:** M · **Риски:** R06, R07 · **Зависимости:** T04, T05.

Freshness скрипт падает при missing/error, проверяет production storage и согласован с расписанием обновления.

**Статус:** реализован и локально проверен; [readiness, лимиты и gate выпуска](FRESHNESS.md), [результаты](PROGRESS.md). `/health/ready` со строгим контрактом, единая таблица лимитов для эндпоинта и CI-скрипта, gate `align_issue` во всех entrypoints, compose-гейт caddy по readiness. Подпись/проверка sha256 бандла и heartbeat worker'а осознанно не входят в этап (T14/T13).

### Контур B · Данные, научная честность и рекомендации

#### T08 · P0 · Сквозной as-of и устранение временных утечек

**Владелец:** ML · **Размер:** XL · **Риски:** R08, R06 · **Зависимости:** T01, формат контекста T04.

Добавить контекст выпуска с observation cutoff и доступностью источников. Отсекать train по концу цели с учётом задержки публикации. Перенести fit PCA/EOF, нормировок, blend, alpha и postprocessors внутрь временных folds; исключить LOYO по будущим годам. Ввести purge/embargo для пересекающихся сезонных окон.

**Приёмка:** изменение любых данных после cutoff не меняет прогноз до cutoff; сезон декабрь–февраль не попадает в train в декабре; каждая train/calibration/test запись имеет проверяемый временной интервал. Если исторические vintages недоступны, явно различаются replay на пересмотренных данных и реальная prospective-проверка.

**Статус:** реализован и локально проверен; [контракт as-of и схема walk-forward](ASOF.md), [результаты](PROGRESS.md). Контекст `asof-v1` публикуется в каждом LIVE-ответе и валидируется до ответа; train отсекается по концу целевого окна с запасом на задержку публикации; blend/калибровки/режимная климатология/shrink подгоняются только внутри прошедших фолдов (walk-forward вместо LOYO); записи бэктеста и ledger несут проверяемые интервалы и метку `replay_revised`/`prospective`. Пространственный пересчёт по локальным фактам и единый pipeline артефактов — T09/T10.

#### T09 · P0 · Один pipeline для LIVE, hindcast, audit и refit

**Владелец:** ML + BE · **Размер:** XL · **Риски:** R09 · **Зависимости:** T08.

Выделить чистый расчётный сервис, переиспользуемый API, CLI и аудитом. Едиными сделать feature schema, model set, blend, калибровки, regime/shrink guards и преобразование в физические единицы. Если tp alpha запрещён политикой, запрет проверяется непосредственно общим inference-путём независимо от JSON.

**Приёмка:** на одном snapshot/as-of/наборе параметров все entrypoints возвращают одинаковые P/Q в заданной численной погрешности; тесты покрывают monthly lead 1–6 и разрешённые seasonal leads. Непроверенные leads API отклоняет. Артефакт с неподходящими моделями/feature schema не загружается молча.

**Статус:** реализован и локально проверен; [единый расчётный pipeline](PIPELINE.md), [результаты](PROGRESS.md). Ядро `forecast/pipeline.py` (`prepare_artifacts`/`predict_target`/`nn_for`) обслуживает LIVE API, worker, CLI, аудит и историческую проверку; engine бэктеста строит records тем же вызовом и пишет таблицу финального blend, которую тест сверяет с LIVE-ответом до 1e-12; `run_hindcast` читает walk-forward ledger вместо inline-пересборки; NN-альфа для tp запрещена политикой на общем пути независимо от содержимого JSON; загрузчики артефактов fail-closed по схеме и набору моделей.

#### T10 · P0 · Пересчитать пространственный навык по локальному факту

## 6. Предлагаемые SLO и quality gates

Ниже **целевые ориентиры, а не измеренные свойства текущего приложения**. Утвердить после профилирования T22 и не переносить молча между разным железом.

| Область | Начальная цель пилота | Как проверять |
|---|---|---|
| Доступность API | 99.5% за 30 дней | Внешний синтетический запрос и readiness, не только process alive |
| Быстрые API | p95 ≤500 мс при 10 RPS | 20 минут нагрузки при двух активных расчётах на согласованном стенде |
| Точечный расчёт | p95 running time ≤60 с для подготовленной точки/3 месяцев | Без queue wait; отдельно измерять cold start и ожидание |
| Поле КРА | p95 running time ≤10 минут, 28 точек | 2 вычислительных worker slots; фиксированные bundle/seed |
| Перегрузка | Ограниченная очередь, 429/503 сверх квоты | Burst-тест постановки; отсутствие безграничных процессов/памяти |
| Качество выдачи | 0 немаркированных stale/unsupported/partial прогнозов | Негативные сценарии и счётчик по каждому выпуску |
| Восстановление | Предложение: RPO ≤1 ч, RTO ≤60 мин | Реальное восстановление БД, очереди и bundle; согласование с владельцем |
| Научный допуск | Паритет pipeline, отсутствие утечек, корректный baseline | Тесты as-of, independent calibration и локальных фактов |
| Заявление о навыке | Только по заранее определённому протоколу | RPSS с интервалом/размером выборки по variable/mode/lead/region; иначе no-skill |

Не копировать текущий mini5 gate `72–85% coverage` как универсальный критерий: он не учитывает независимость calibration/test, размер выборки и ширину интервала. Отдельно сравнивать с равновероятностной и адаптивной климатологией; простая доля попаданий не заменяет вероятностный score.
