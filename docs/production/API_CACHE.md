# T04 · HTTP-контракты и идентичность кэша

Дата: **2026-09-05**. Контракт: **`api-v1`**, политика: **`closed-pilot-v4`**.

[Прогресс](PROGRESS.md) · [План](PLAN.md) · [Identity и запуск](IDENTITY.md) · [Scope пилота](PILOT.md)

## Результат и границы

Добавлены общие Pydantic-контракты, типизированные ответы, единая ошибка, версия сорта и параметризованный кэш результата. **Расчёты по HTTP не включены.** Формат корректного запроса и разрешение выполнить его — разные проверки.

`POST /api/prepare` и `POST /api/region/refresh` теперь пропускают operator/admin к валидации тела. Неверный вход получает 422, неподдержанный scope — 403, корректный вход — 403 `pilot_operation_disabled`. Никаких записей `JOBS`, потоков или фиктивных queued jobs эти обработчики не создают. Reader получает 403 по роли раньше проверки тела; аноним — 401. Origin/CSRF из T02 сохраняются.

OpenAPI доступен после входа через **`GET /api/contracts`**. В нём отражены cookie/CSRF/Origin, error responses и `x-pilot-computation-enabled=false`. Swagger и публичный `/openapi.json` не открыты. Неиспользуемые старые `/api/inside`, `/api/years`, `/api/ledger` не рекламируются как доступный контракт и остаются закрыты default-deny политикой. Альтернативный engine API остаётся HTTP 410.

## Входные модели

### Точечный запрос

```json
{
  "lat": 46.25,
  "lon": 38.25,
  "point_id": "P01",
  "region": "krai",
  "start": "2026-10",
  "horizon": 3,
  "mode": "seasonal",
  "season_len": 3,
  "kind": "forecast",
  "variables": ["t2m", "tp"],
  "variety_id": null,
  "variety_revision": null
}
```

Это пример **валидной формы**, не разрешённого запуска.

- Координаты — конечные JSON-числа WGS84: широта −90…90, долгота −180…180. `NaN`, Infinity, boolean, строковые координаты и долготы 0…360 за допустимым диапазоном не нормализуются молча.
- `start` обязателен: ровно `YYYY-MM`, 1900–2099, месяц 01…12; нет пустого/default `2026-10`, дополнительных дней или пробелов.
- `kind`: `forecast` / `hindcast`. Старый неиспользуемый `year` и неизвестные поля дают 422. У hindcast всё окно должно помещаться в 2004-01…2024-12; это ограничение формы, не подтверждение качества этих лет.
- `mode`: `monthly` / `seasonal`; `horizon` — целое число месяцев 1…6, без дробей, строк и bool.
- Monthly имеет `season_len=1`, seasonal — `season_len=3`. Если поле отсутствует, используется документированный default по mode; явно неверное значение не исправляется.
- Запрос вычисления должен содержать полные периоды: seasonal horizon допускает 3 или 6, не молчаливое округление 1/4/5 месяцев до сезона.
- `variables` — непустой уникальный набор `t2m`/`tp`.
- `variety_id` — UUID, `variety_revision` — положительное целое; пара передаётся вместе или оба значения отсутствуют/null. Имена и client-supplied releases/owner не принимаются вместо этой пары.
- Проверка scope отдельно ограничивает HTTP фиксированными P01–P28 Краснодарского края. `point_id`, если указан, должен совпадать с координатами; другие регионы/точки не становятся доступными из-за валидного enum.

### Региональный запрос

`start` обязателен, `region` имеет enum. Текущий алгоритм регионального поля рассчитан на **seasonal / horizon=3 / season_len=3 / t2m+tp**. Другие комбинации отвергаются, а не используются для чтения поля с другими параметрами. В HTTP все такие вычисления по-прежнему запрещены пилотом.

### Данные пользователя

Численные поля площади/сорта не принимают boolean, numeric strings, нечисловые значения. Текстовые значения не допускают NUL и одиночные Unicode surrogates, которые невозможно корректно сохранить в PostgreSQL. Имена с кавычками, тегами, Unicode и `/` сохраняются как данные; доступ к записи идёт по UUID.

Настройки подписок сохраняют `start_month`, `horizon`, `mode`, `season_len`, `variables`, пару сорта/версии и `active=false`. Неверный месяц, нецелый горизонт, несовместимая длина сезона, повторенные/неизвестные variables и псевдо-boolean отклоняются. Сорт проверяется внутри организации, его версия — по текущей записи; чужой даёт 404, устаревшая версия — 409.

Подписка пока **неисполняемое предпочтение**, не запрос forecast. Диапазон horizon=1…6 сохраняется и для старых seasonal preferences; значение 1 не переписывается в 3. Превращение такой настройки в задачу должно дополнительно проходить `ForecastSpec` с требованием полного периода. Активация/рассылка не реализованы. T05 добавил явный snapshot/import/quarantine для старого unowned SQLite registry без угадывания владельца; исполнение остаётся T06.

## Query, JSON и ответы

- Списки принимают только `limit=1…100`; дробная запись `1.0`, boolean, повторение параметра и неизвестные `owner_id`/`organization_id`/другие поля дают 422, а не игнорируются.
- Для новых JSON-запросов отвергаются повторяющиеся ключи, не-UTF-8, NaN/Infinity и числовое переполнение. Ограничение тела 16 KiB и проверки доступа выполняются до обработчика.
- Активные account/resource/history endpoints имеют Pydantic response models. У исторических value/skill и тела сохранённой job остаётся явно opaque JSON-часть: она не объявлена валидированной научной моделью.
- Отсутствующий/нечитаемый исторический artifact больше не возвращается как успешный `200 {ok:false}`. Ответ — 503 с кодом `artifact_unavailable`.
- Ошибка сериализации/несоответствия response model — безопасный 500 `invalid_response`, без вывода исходной записи или validation input.

Единый формат ошибки, с необязательным `detail`:

```json
{
  "code": "invalid_request",
  "error": "invalid_request",
  "detail": [
    {"loc": ["body", "start"], "type": "string_pattern_mismatch", "msg": "..."}
  ]
}
```

Пароли и другие значения `input`/`ctx` в ошибку не возвращаются. CSP/no-store/остальные защитные заголовки T03 сохраняются. Для 405 сохраняется `Allow`, для лимитов — `Retry-After`.

Создание обычных metadata records — 201, чтение/изменение — 200, удаление/logout — 204. Контракт **асинхронного принятия** — 202, `job` UUID, `status=queued`, `status_url` и совпадающий `Location: /api/jobs/<uuid>`. Транспортный helper проверен тестом, но **пока ни один HTTP-запрос вычисления не принимается**: вместо имитации очереди остаётся 403. Durable dispatcher/state machine выполняются в T06.

## Версия сорта и миграция

T04 добавил миграцию **`0002_crop_revision`**, поверх `0001_identity`. Текущий head после T05 — **`0003_persistent_state`**; [schema/state runbook](STATE.md). Изменения revision:

- `crops.revision` — положительное целое с начальным значением 1.
- Каждое обновление атомарно увеличивает revision, в том числе при нескольких изменениях в одну секунду. `updated_at` не используется как версия.
- ID, owner, organization, JSON и timestamps существующих записей не переписаны; сохранность проверена на SQLite и PostgreSQL.
- `IdentityService.variety_snapshot()` разрешает сорт в контексте организации и возвращает UUID/revision/SHA-256 фактического содержимого. Текст имени не является идентичностью.

Перед использованием обновлённого API нужна миграция. Без актуальной версии схемы startup identity остаётся fail-closed. При настроенных переменных из [IDENTITY.md](IDENTITY.md):

```bash
cd AgroCast
../.venv/bin/python -m agrocast.identity.cli migrate
../.venv/bin/python -m agrocast.identity.cli check
```

Для Compose сначала собрать новый image, применить миграцию, затем перезапустить API. Перед изменением реальной БД сделать backup и согласовать остановку записей; тестовое downgrade/reapply не является проверенным production rollback/restore.

## Полный ключ результата

`ResultIdentity` сериализуется каноническим JSON, его SHA-256 определяет путь:

```text
<data_root>/results-v1/<sha256-of-identity>.json
```

В идентичность входят:

1. Версия формата ключа и операция `point`/`region`.
2. Namespace; для личного результата — owner и organization, заданные сервером, не пользователем.
3. Регион и точные координаты/point ID либо fingerprint всей региональной сетки.
4. `start`, `horizon`, `mode`, `season_len`, `kind`, канонический набор variables.
5. UUID, revision и content hash выбранного сорта, если он есть.
6. Явные `data_release`, `model_release`, `application_release`.
7. Fingerprint существенных настроек; региональный resolver включает конфигурацию world, defaults точек, seed/численность ансамбля через Config, шаг поля, параметр detrend и версию алгоритма.

Порядок ключей JSON/variables не меняет эквивалентный ключ. Близкие координаты не округляются в один результат. Дополнительно убрано двухзначное округление в имени рабочей директории точки; `ready.json` этой директории всё ещё не является versioned result cache или readiness из T07.

Общий ключ реализован и проверен для точки и региона. **В существующий путь вычисления включён региональный кэш**; новый кэш точечных forecast/job пока не активирован до T06 и допуска вычислений.

### Запись и чтение

Файл содержит точную identity, её ключ, состояние `complete`, время публикации и checksum payload. При чтении проверяются identity/key/checksum/структура; неподходящий, частичный, повреждённый или будущий timestamp означает cache miss. Затем применяется TTL по записанному времени, не по filesystem mtime. Копирование октябрьского файла под мартовский ключ или `touch` не создаёт hit.

Запись — во временный файл с последующим `fsync`/атомарным `os.replace`; неуспех не уничтожает предыдущий корректный результат. Несколько ключей сосуществуют, глобального `latest` файла нет. Перед публикацией региональный builder проверяет совпадение результата каждой ячейки с запрошенными координатами/месяцами, допустимость вероятностей и неизменность сетки/конфигурации относительно начала. Это проверка контракта результата, не доказательство прогностического навыка.

Существующий offline региональный scheduler теперь сравнивает полный ключ текущего start/releases/settings, а не возраст любого файла региона. При смене месяца или релиза свежий старый файл не подходит.

### Releases не выдумываются

Нет fallback `latest`, `unknown` или mtime вместо data/model version. Для offline регионального вычисления нужен `AGROCAST_RELEASE_MANIFEST_FILE` либо явно переданный объект `Releases`. Файл содержит **три 64-символьных SHA-256 идентификатора**: `data_release`, `model_release`, `application_release`. Они должны приходить от доверенного release process и обозначать неизменяемые входы/модели/код; подстановка произвольных hex-строк ради запуска недопустима.

T04 **не создаёт и не аттестует реальные releases**. T05 разделяет read-only bundle и writable state; проверка подлинности manifest, аттестация неизменяемого release, отсутствие изменений всех входов во время расчёта, полный provenance и rollback остаются T14/T15. Checksum кэша защищает от смешивания/случайной порчи, не от атакующего с правом переписать файл и checksum. Отсутствие release identity закрывает повторное использование/построение этого кэша, а не даёт ложную актуальность.

У существующего CLI теперь обязателен start:

```bash
cd AgroCast
../.venv/bin/python -m scripts.krig_demo --start 2026-10 --release-manifest /secure/releases/identity.json --workers 2
```

Эта команда только для осознанного offline research, не разрешение на production-прогноз. Агент её с реальными расчётами не запускал.

### Старые файлы

`audit/krig_demo_tp.json`, `audit/<region>_field.json` не мигрируются и не считаются hit нового кэша. Их чтение осталось только через явно названные `legacy_field_path`/`legacy_field_age_s`; digest подписывает их как архив без ключа результата. Старый freshness script относится к этим legacy artifacts и не является readiness нового контура — T07 остаётся открытым.

## Проверки

Тесты покрывают ошибки до worker, полные периоды, enum/finite/strict types, duplicate JSON/query, response validation, особые имена, subscriptions round trip, revision migration, различные key dimensions, отсутствие collision март/октябрь, stale/checksum/partial/mismatch, неуспешную атомарную публикацию, конкурентные read/write, настоящий региональный builder с тестовым вычислителем и scheduler с разными месяцами/releases.

Реальные модели/NOAA в cache tests не запускаются. Новые численные утверждения и прохождение science gates не заявляются. [Точные результаты, версии и ограничения](PROGRESS.md).


## Дополнения T05

Read-only owner-scoped `/api/publications` и `/api/publications/{UUID}` возвращают typed historical response с job reference и checksum; PUT/POST/DELETE не открыты. Удаление job с publication даёт 409. В `CropBody` сохранены legacy `maturity`, `sow_from`, `sow_to`, `area_ha`; пустое окно сева означает неизвестное, заданное проверяется как календарное ММ-ДД. Разрешение на вычисления не изменено. Запуск теперь через `agrocast.serve.product:create_app --factory`; invalid configuration не оставляет placeholder API. [Подробности](STATE.md).
