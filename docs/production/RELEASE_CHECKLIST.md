# Проверяемый чек-лист production-релиза

[План](PLAN.md) · [Исходный аудит](AUDIT.md)

Дата исходного состояния: **2026-09-05**. Все пункты ниже — **требования к будущему релизу, не отметки о выполнении**. Новые endpoints, очередь, manifests и метрики из этого документа ещё требуется реализовать. Зелёный текущий pytest/mini5 не закрывает этот чек-лист автоматически.

## Правило go/no-go

Релиз разрешается только для перечисленных в его scope возможностей. Каждый gate подтверждается артефактом из CI/staging/пилота и ответственным. Невыполненный P0 — **no-go**. Исключение допустимо для функции, которая действительно отключена через API и UI и не фигурирует в обещаниях продукта; предупреждение мелким шрифтом не заменяет исправление.

Научный no-go может означать выпуск только экспериментального сервиса или климатологии, без обещания подтверждённого навыка и без непроверенных агрорекомендаций. Пороговые значения научных метрик определяются заранее, а не после просмотра результата.

## Паспорт релиза

| Поле | Что зафиксировать |
|---|---|
| Release ID / дата | Уникальный ID и UTC-время выпуска |
| Код и окружение | Commit, image digest, dependency lock hash, schema migration version |
| Данные и модели | Data snapshot ID, model bundle ID, checksums и validation run ID |
| Scope | Регионы/точки, культуры, переменные, mode, lead, season_len |
| Ограничения | Experimental/no-skill/fallback, недоступные функции и причины |
| Ответственные | PO, BE, ML, Ops, QA; агроном для рекомендаций |
| Evidence | Ссылки на тесты, научный отчёт, security scan, load, backup/restore и pilot review |
| Откат | Предыдущий image и совместимый bundle, безопасная схема БД и критерий rollback |
| Решение | Go/no-go, дата и согласующие лица |

## G01 · Безопасность и границы API

Ответственные: BE + QA. План: T01–T04, T23.

- [ ] Аноним не может менять справочник, подписываться от чужого имени и запускать защищённые расчёты; 401/403 проверены HTTP-тестами.
- [ ] Пользователь A не читает/не меняет jobs, отчёты и поля B; угадывание ID не даёт доступа.
- [ ] У альтернативного API/CLI/admin endpoints нет непреднамеренного публичного обхода защиты.
- [ ] Некорректные mode/kind/даты/границы/NaN/Infinity/season_len и неизвестные поля отклоняются до постановки задачи.
- [ ] Превышение размера тела, квоты и concurrency даёт документированный отказ; дорогая работа не начинается.
- [ ] XSS-проверки проходят на сохранённых именах, селекционере, localStorage-полях, ошибках и выводе отчёта; текст отображается буквально.
- [ ] CSP, доставка static assets, cookie/CSRF-политика при использовании сессий и TLS проверены в реальном браузере.
- [ ] Secrets отсутствуют в репозитории, логах и клиентском коде; сканирование имеет результат и процесс разбора находок.

**Evidence:** HTTP contract suite, браузерный security E2E, security/configuration review.

## G02 · Жизненный цикл задачи и сохранность результата

Ответственные: BE + Ops + QA. План: T05, T06, T15.

- [ ] Перезапуск API не теряет job ID, статус и ссылку на отчёт.
- [ ] Принудительное завершение worker переводит задачу в предусмотренное состояние; retry не создаёт второй выпуск.
- [ ] Две API-реплики видят одинаковые jobs; пользователь получает результат независимо от реплики.
- [ ] Идентичные запросы дедуплицируются, разные даты/версии модели/сорта не объединяются.
- [ ] Deadline, отмена, heartbeat, лимит attempts, очистка и retention проверены, не оставляют неограниченные процессы.
- [ ] Потеря Redis не уничтожает единственную копию очереди/результата: pending jobs восстанавливаются из БД.
- [ ] Пересоздание контейнера сохраняет пользователей, сорта, подписки, forecasts, scores и историю выпусков.
- [ ] Миграции проходят на копии реальных данных; сверены записи и права доступа.

**Evidence:** restart/concurrency integration suite, журнал миграции и reconciliation.

## G03 · Readiness, актуальность и целостность данных

Ответственные: ML + Ops. План: T07, T13, T14.

- [ ] Liveness отличает живой процесс от готового сервиса; readiness возвращает 503 при отсутствии обязательного bundle/источника/БД/очереди.
- [ ] Свежесть проверяется по manifest/дате доступности и последнему полному predictor frame, не по времени checkout или только daily_region.
- [ ] В списке источников явно учтены soil, stratosphere, snow, regimes и land/ocean features, когда они нужны разрешённому pipeline.
- [ ] Missing/corrupt/timeout/ошибка проверки не превращаются в успешный health/freshness.
- [ ] Октябрьский запрос не маркируется lead-1 при февральском cutoff; эффективный lead входит в ответ и support matrix.
- [x] Частичные месяцы и all-NaN осадки не считаются полным нулевым фактом. <!-- test_source_refresh_t13: drop_incomplete_months (ingest gate) -->
- [x] Неудачная загрузка/обучение оставляет прошлый согласованный release доступным; новый снимок публикуется атомарно. <!-- test_bundle_release_t14: build/publish corrupt-safe, concurrent reader -->
- [ ] Scheduler запущен единственным владельцем; TTL полей, SLA источников, расписание и алерты согласованы.
- [ ] Монитор проверяет storage действующего окружения, а не только файлы репозитория.

**Evidence:** data quality report, failure-injection suite, manifest и реальный freshness alert.

## G04 · Временная и пространственная честность

Ответственные: ML + независимый reviewer. План: T08–T10.

- [ ] Train содержит только полностью наблюдённые и доступные до cutoff цели, включая конец сезонного окна.
- [ ] PCA/EOF, нормировки, отбор признаков, blend, alpha, shrink и calibrators не обучаются на будущей части fold.
- [ ] Выполнен тест future-data mutation: изменения после cutoff не изменяют прошлый выпуск.
- [ ] Между train/calibration/test задано временное разделение и embargo для перекрывающихся сезонов.
- [ ] LIVE, hindcast, CLI, региональный worker и аудит используют один pipeline; P/Q совпадают для одинакового контекста в согласованном допуске.
- [ ] Метрики каждой ячейки вычисляются по её локальным наблюдениям/терцилям; разные факты действительно меняют её score.
- [ ] Доверительные интервалы учитывают зависимость по времени и пространству; число строк не выдается за число независимых испытаний.
- [ ] Отдельно опубликованы результаты по variable/mode/lead/region, а не только одна агрегированная цифра.
- [ ] Использованные ранее 2025–2026 годы не объявлены нетронутым holdout без доказательства; для новых заявлений назначен независимый протокол и заморожена модель.
- [ ] Ясно различаются ретроспективный replay на пересмотренных данных, доступность исторических vintages и реально опубликованные prospective forecasts.

**Evidence:** temporal isolation suite, parity matrix, локальные observations, scientific validation report.

## G05 · Калибровка, метрики и пригодность рекомендаций

Ответственные: ML + агроном + PO. План: T11, T12, T16.

- [ ] Определения RPS/RPSS/ECE/coverage и baseline едины в ledger, audit, API и UI; синтетические контрольные примеры проходят.
- [ ] Coverage посчитано на данных вне обучения и калибровки; опубликованы N, интервал неопределённости и ширина прогнозного интервала.
- [ ] Предпосылки выбранного conformal-алгоритма описаны; нет безусловной 80%-гарантии без соответствующего доказательства.
- [ ] Есть сравнение с равновероятностной и адаптивной климатологией; критерий заявления о навыке утверждён до final evaluation.
- [ ] Неподтверждённый навык осадков и деградация ограничивают соответствующие советы в общем коде, не только в UI.
- [ ] Формулы полива проходят проверки единиц: мм → м³/га → м³ на площадь; почвенный запас вычитается в согласованных единицах.
- [ ] Суточные/декадные сценарии и даты сева/морозов имеют отдельную проверку либо отключены/маркированы как непроверенные.
- [ ] Цена имеет source/as_of/stale, условные потери не представлены как гарантированный доход; fallback прозрачен.
- [ ] Верификация ждёт полного observation window; повторный цикл не дублирует scores, исправление факта отслеживается.

**Evidence:** metric fixtures, calibration report, dimension tests, экспертное согласование и негативные policy tests.

## G06 · Происхождение и воспроизводимость выпуска

Ответственные: BE + ML. План: T14, T15, T17.

- [ ] Каждый forecast содержит immutable ID, target interval, issued_at, data_cutoff, model/data IDs, seed и значимые настройки.
- [ ] Manifest связывает code commit, lock hash, feature schema, модели, train/calibration cutoffs и validation run.
- [ ] Checksums полные; их проверка выполняется перед использованием bundle, изменение target/inputs/model меняет digest выпуска.
- [ ] Все monthly/seasonal цели фиксируются в ledger, старые записи не подменяются переобучением.
- [ ] Если обещана проверяемая подлинность, определены подпись/время фиксации и независимая проверка; обычный hash не называется защитой от переписывания.
- [ ] По сохранённому manifest воспроизведён выбранный прошлый выпуск с заданным численным допуском.
- [ ] Код и большие runtime-данные разделены; источники и лицензии bundles доступны в inventory.

**Evidence:** manifest, replay report, integrity/concurrent-write tests, источник временной фиксации при наличии такого обещания.

## G07 · CI, контейнер и deployment

Ответственные: Ops + BE. План: T17, T18, T20.

- [ ] Обязательные lint/type/unit/HTTP/integration/scientific gates проходят; branch protection и требуемые статусы проверены в GitHub.
- [ ] Fast CI не зависит от внешних котировок/погоды; длительный аудит сохраняет отчёты и не использует несовместимый stale-кэш.
- [ ] Новый критический код покрыт сценариями и ветвями, а не только достижением процента coverage.
- [ ] Новый/изменённый код не содержит комментариев и поясняющих docstring; исключения линтера не спрятаны в inline suppression.
- [ ] Dependency/image scans разобраны с различением runtime, build tooling и тестового окружения; нет неисследованных блокирующих находок.
- [ ] Чистая Docker-сборка выполнена; проверены native libraries, non-root, writable volumes, CPU/RAM/PID limits и SIGTERM.
- [ ] Prod startup не устанавливает зависимости из сети; image/base/Caddy и Actions версии зафиксированы.
- [ ] Staging использует тот же image digest, bundle и путь миграции, что будущий production.
- [ ] HTTPS, proxy/forwarded headers и внешняя readiness проверены; development preview при использовании доступен через `0.0.0.0` и разрешённый host, browser API URL относительные.

**Evidence:** CI run и артефакты, SBOM/scan review, container smoke, внешний deployment smoke.

## G08 · Нагрузка, наблюдаемость и восстановление

Ответственные: Ops + BE + QA. План: T19, T20, T22.

- [ ] Выполнены warm/cold/load/burst-тесты на зафиксированном железе, опубликованы p50/p95, queue wait, CPU и peak RSS.
- [ ] Проверены цели из плана либо заранее согласована новая версия SLO; перегрузка не разрушает данные и не блокирует health.
- [ ] Есть correlation request → job → forecast; errors/retries/missing models и stale predictions измеримы.
- [ ] Алерты на источник, очередь, отказ worker, хранилище, диск и readiness реально доходят ответственному.
- [ ] Проведён restore в пустое окружение: БД, bundles, конфигурация и восстановление pending jobs; RPO/RTO измерены, а не заявлены по наличию backup-файла.
- [ ] Отрепетирован rollback image + model/data release с учётом совместимости схемы БД.
- [ ] Данные пользователей и secrets в backups/логах защищены; retention и удаление проверены.

**Evidence:** load report, alert drill, restore/rollback журнал с временем и сверкой записей.

- [ ] Сценарий карта → параметры → расчёт → отчёт → повторное открытие проходит на desktop/mobile и с клавиатуры.
- [ ] Проверены 404 потерянной/удалённой задачи, 401/403/422/429/503, сетевой сбой, отмена, stale/no-skill и отсутствие карты/котировки.
- [ ] Polling имеет ограничение времени/backoff, null-поля не ломают страницу; нет `[object Object]`.
- [ ] Дата входов, фактический lead, региональная доступность, норма, предупреждения и происхождение цены согласованы между API, UI и печатью.
- [ ] README, инструкция запуска, модельная карточка и API capabilities описывают фактически поставляемый продукт.
- [ ] Согласованы лицензия кода, условия источников/тайлов/котировок и перераспространения данных; доступны privacy/terms и способ поддержки.

**Evidence:** E2E/browser report, пример обычного и degraded-отчёта, документация релиза и inventory прав.

## G10 · Пилот и решение о включении публичного доступа

Ответственные: PO + ML + Ops + QA.

- [ ] Закрытый пилот длится минимум 14 дней; собраны ошибки, метрики задач, свежесть и обратная связь по понятности предупреждений.
- [ ] У пилота нет неразобранных потерь данных, обхода прав и silent stale forecasts; серьёзные инциденты исправлены и повторно проверены.
- [ ] Есть владелец поддержки, канал инцидентов, правила rollback и дежурного реагирования.
- [ ] Для новых научных обещаний есть отдельные достаточные свидетельства; 14 дней uptime не названы доказательством сезонного навыка.
- [ ] Все применимые gates G01–G09 подписаны, ограничения и отключённые функции перечислены в паспорте.
- [ ] Go/no-go зафиксировано явно. Изменение data/model bundle после review запускает затронутые gates заново.

## Минимальные сценарии реагирования

Это проект будущих runbook; конкретные команды и владельцев добавить в T19/T20 до выпуска.

| Событие | Первое действие | Условие восстановления |
|---|---|---|
| Устарел обязательный источник/predictor frame | Остановить новые неподдерживаемые выпуски; readiness/degraded; уведомить владельца данных | Проверенный новый snapshot, согласованный bundle и повторный smoke; не увеличивать TTL ради зелёного статуса |
| Worker завершился или очередь растёт | Ограничить admission, сохранить pending state, проверить lease/ресурсы | Идемпотентное восстановление очереди, контролируемые retries, отсутствие дублей |
| Corrupt bundle/неудачный refit | Не продвигать staging; вернуть указатель на последний проверенный release | Checksums/schema/parity/data gates проходят; старые выпуски не переписаны |
| Уязвимость или утечка пользовательских данных | Ограничить затронутую поверхность, сохранить необходимые следы, привлечь ответственного | Исправление, ротация затронутых secrets при необходимости, повторная security-проверка и процесс уведомления |
| Новый аудит отменяет прежний навык | Пометить model release, отключить связанные советы/claims, сохранить прежние опубликованные результаты | Новый независимый протокол и review; никаких выборочных удалений неудачных прогнозов |
| Потеря БД/volume | Остановить запись, запустить отрепетированный restore | Сверка выпусков/пользователей/оценок, восстановление очереди, проверенный RPO/RTO и incident review |
