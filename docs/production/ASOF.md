# Сквозной as-of и устранение временных утечек (T08)

Документ описывает контракт `asof-v1`, правила отсечки и walk-forward схему оценки.
Реализация: `agrocast/forecast/asof.py`, `features/dataset.py`, `backtest/engine.py`,
`skill/ledger.py`, `blend/regime_clim.py`, `forecast/orchestrator.py`.

## Контекст выпуска (schema `asof-v1`)

Каждый ответ прогноза содержит блок `as_of`, собираемый `release_context()` и
проверяемый `validate_context()` перед публикацией:

| Поле | Смысл |
| --- | --- |
| `issue_month` | месяц выпуска (первый целевой месяц, `start`) |
| `observation_cutoff` | последний полностью доступный наблюдательный месяц = `min(issue-1, доступность источников)` |
| `publication_delay_days` | задержка публикации месяцев (конфиг `publication_delay_days`, по умолчанию 5) |
| `train_cutoff` | граница обучающих окон: `observation_cutoff - months_of_delay(delay)` |
| `sources` | для каждого источника — последний полный месяц; источник не может быть помечен доступным позже cutoff |
| `evaluation` | `replay_revised` или `prospective` (см. ниже) |

Инвариант `validate_context`: `train_cutoff ≤ observation_cutoff ≤ issue_month`.
Поле ответа `issue_data_through` теперь равно `observation_cutoff`, а не формальному
`issue` — это месяц, данными до которого реально построен прогноз.

Задержка считается консервативно в месяцах: `months_of_delay(d) = ceil(d/31)`, то есть
любое положительное внутримесячное запаздывание сдвигает обучающую границу на полный
месяц. Для ERA5 monthly (публикация ≈ 5 дней после конца месяца) прогноз, выпускаемый 1-го
числа, не видит данных предыдущего месяца — и не использует их.

## Отсечка train по концу цели

`training_data(..., until=cutoff, span, embargo)` отсекает обучающий пример, только если
**весь целевой окно** (для сезонного режима — `span` месяцев) с учётом `embargo` завершается
не позже `cutoff`. Раньше обрезка шла по началу окна, и сезонная выборка с целью,
стартующей в cutoff, затягивала наблюдения на 2 месяца за границу. Теперь сезон
декабрь–февраль физически не может попасть в train, если февраль ещё не наступил:
проверка `target_allowed()` и прямой тест `test_seasonal_target_window_purged_from_train`.

LIVE-контур (`_fit_predict_target`) и бэктест используют одну и ту же функцию, поэтому
строка предикторов, ряды nn-ядра, режимный guard, regime-фичи и ospr-спред берутся из
строки `cutoff`, а не `issue`.

## Walk-forward вместо LOYO

Оценка blend в ledger больше не использует «leave-one-year-out по всем остальным годам» —
в том числе будущим. Фолды строятся функцией `walk_forward_masks(target_ends, fold_years,
embargo)`: в обучающую выборку фолда года `y` попадают только записи, чей целевой интервал
заканчивается строго до `y-01` минус эмбарго (эмбарго = `span-1`, для сезонного окна —
2 месяца, что отсекает сезоны, пересекающие границу фолда, например январь-февраль
предыдущего DJF).

Для каждого фолда заново подгоняются: веса Blender, терцильный калибратор,
conformal-квантили, режимная климатология (`RegimeClimatology.fit_history(...,
until_period=граница фолда)`), shrink-контекст (навыки только прошедших лет). Каждая строка
ledger получает поле `fold_train_until` — максимальный целевой месяц, использованный при
подгонке этого фолда; оно обязано быть меньше начала года фолда. `test_ledger_folds_only_use_past_records`
проверяет это на всех строках.

Skill-map бэктеста строится из walk-forward ledger, а не из in-sample blend; если ledger
построить не удалось, сохраняется прежний путь с честной пометкой
`skill_source="in_sample_fallback"` в артефакте.

## Проверяемые интервалы записей

Каждая запись `backtest_records_*.parquet` содержит `issue`, `observation_cutoff`,
`train_until`, `train_n`, `target_start`, `target_end`. Инварианты (тест
`test_backtest_records_carry_verifiable_intervals`): `observation_cutoff == issue -
months_of_delay(delay)`, `train_until == observation_cutoff`, `target_start > issue`,
`train_n ≥ 18`. Изменение наблюдений после cutoff не меняет записей раньше cutoff —
это проверяет `test_future_data_cannot_move_earlier_predictions`: два прогона бэктеста на
синтетическом хранилище и на его же префиксе, дополненном будущими месяцами, дают
побитово равные таблицы (`check_exact=True`).

## Replay против prospective

Если исторические винтажи входов недоступны (по умолчанию так и есть), вся бэктест-оценка
честно помечается `evaluation="replay_revised"`: пересчёт идёт по **пересмотренным**
наблюдениям и текущему пайплайну, и оптимистичность такой оценки осознанна. Реальная
prospective-проверка — накопленный `append_live`-журнал прогнозов, выпущенных до наступления
цели, плюс винтажи: если создать каталог `vintages_dir/<issue>/` со снапшотами входов,
`evaluation_mode()` переключит соответствующие прогоны в `prospective`. Флаг хранится в
записях records и ledger и не позволяет выдать replay за prospective.

## Где утечек не было (аудит 2026-09-06)

- Адаптивная климатология `adaptive()` строится по месяцам строго `≤ year-1` целевого периода.
- SST EOF (PC1–3) нормированы на фиксированный базовый период `base_start..base_end`,
  аномалии и сглаживание — trailing.
- `PooledNN.fit(..., max_target_year)` исключает год фолда и всё, что позже него.
- LIM-переходы обучаются на данных до `01-января` года выпуска (`fit_lim_monthly`).
- `window_skill` shrink использует навыки строго `< year`.
- ospr-спред берётся из строки issue-моента предикторов, наблюдений цели не касается.
- Станционная калибровка целей ограничена `calib_end_year`.
- Границы терцилей цели (`e1/e2`) — из той же trailing-климатологии, без данных цели.

## Конфигурация

- `publication_delay_days` (int, по умолчанию 5; 0 — отключить сдвиг, только для синтетических
  проверок; прошедшие валидацию неотрицательные значения).
- `vintages_dir` (путь; пусто — replay-режим по умолчанию).

## Тесты

`tests/test_asof.py` (9): границы `months_of_delay`; контракт/валидация контекста;
`target_allowed`; винтаж-пробник replay/prospective; purge сезонных окон (плюс embargo);
walk-forward маски на seasons через границу фолда; fold-гигиена ledger; побитовая
инвариантность прогнозов к будущим данным; интервальные поля records. Дымовой тест
сезонного LIVE дополнительно проверяет наличие и согласованность блока `as_of`.
