# Готовность и свежесть входов (T07)

Документ описывает разделение проверок живости/готовности, обязательные источники для каждой
возможности и правило «даты из манифеста, а не mtime». Реализация:
`agrocast/serve/readiness.py` (вся логика), `/health/ready` в `serve/product.py`,
`scripts/zarr_freshness.py` — тонкий printing-слой поверх того же модуля.

## /health/live против /health/ready

- `/health/live` — «процесс жив»: отвечает всегда, без доступа к данным. Используется
  Docker HEALTHCHECK и лаунчером десктопа (окно должно открыться даже на устаревших данных,
  чтобы пользователь видел объяснение).
- `/health/ready` — «данные годны для расчёта»: 200 только когда все обязательные проверки
  зелёные; иначе 503 со списком причин. Публичный GET (как live), без ролей.

Тело ответа (модель `ReadinessResponse`, строго по контракту):

```json
{
  "status": "ready | not_ready",
  "reasons": ["daily_region:stale", "bundle:corrupt", "db_unavailable"],
  "degraded": ["sst:missing", "region/krai:skill_stale"],
  "sources": {"daily_region": {"status": "ok", "last": "...", "available_at": "...", "age_days": 9, "limit_days": 14}},
  "bundle": {"status": "ok", "contract": "world-v1", "manifest_present": true},
  "regions": {"krai": {"grid": "ok", "skill": "ok", "skill_generated_at": "...", "skill_age_days": 5}},
  "queue": {"status": "ok", "jobs": {"succeeded": 3}, "oldest_queued_age_s": 41}
}
```

## Обязательные и опциональные источники

Принадлежность к «обязательному» — единственный источник истины в коде, из него же читает
скрипт свежести:

| Источник | Категория | Лимит, дней |
|---|---|---|
| `daily_region` | обязателен | 14 |
| `fields_monthly` | обязателен | 60 |
| `sst`, `strat_snow`, `oisst_boxes`, `regimes` | опциональны (деградация) | 120 / 60 / 90 / 365 |

- Отсутствие, ошибка чтения, пустой или устаревший **обязательный** источник → 503 и причина
  `имя:missing | error | empty | stale | incomplete_last_row`.
- То же для **опционального** — только явная пометка в `degraded`, ответ 200. Физика без
  этих источников считается, но честность результата требует показывать отсутствие.
- `incomplete_last_row` — последняя строка предсказорного фрейма содержит NaN: строка
  считается неполной, публикация с таким issue недопустима, даже если календарная дата свежая.
- `available_at` источника = дата последней полной строки (не календарь и не mtime).
  Политику календарных задержек публикаций вносит T08 (as-of), здесь — факт по данным.

## Манифест бандла и даты вместо mtime

- Дата предсказорных входов берётся из zarr-координаты `time` (данные), возраст артефактов
  навыка — из внутреннего поля `generated_at` файла `{region}_grid_skill.json` (манифест
  артефакта). Файловый mtime нигде не является критерием готовности.
- Для runtime-«поля» региона (`state/compute`) манифест-даты нет — скрипт печатает возраст по
  mtime с явной пометкой «filesystem-время, даты в манифесте нет»; это предупреждение
  оператора, не порог `/health/ready`.
- `world/ready.json` — манифест бандла. Минимум `{"ok": true}`. Новые бандлы обязаны писать
  поля: `contract` (совместимость — см. ниже), `built_at`, `predictor_through` (до какой даты
  в бандле полные предсказорные данные).
- `contract` не совпал с `world-v1` приложения → 503 `bundle:contract_mismatch`.
- `predictor_through` позже, чем данные в сторе → 503 `bundle:manifest_ahead_of_store`
  (бандл обещает больше, чем содержит). Поле `built_at` на этом этапе справочное.
- У бандлов до T07 полей может не быть — это допустимо (`manifest_present` в выводе), дата
  тогда определяется только по стору.

## Очередь и база

`/health/ready` при наличии `app.state.identity.engine` читает `jobs` (счётчики по статусам и
возраст старейшей queued-записи). Недоступная или немигрированная БД → причина
`db_unavailable`, 503. Сам факт queued-ожидания в очередь не влияет на готовность (SLA
воркера — зона T13); при `engine=None` (тесты) блок `unavailable`, не ошибка.

## Gate честного выпуска (октябрь как lead-1 на февральских входах)

`agrocast.forecast.orchestrator.align_issue(start, index)` — единая точка для всех
entrypoints:

- явный `start`: месяц выпуска `start-1` обязан существовать в предсказорном фрейме;
  иначе `IssueFreshnessError` — прогноз не вычисляется и не публикуется. В веб-приёме это
  ошибка задачи, в десктопе — 422 `issue_inputs_mismatch` («Запрошенный месяц новее последних
  полных входов»).
- неявный `start`: выпуск якорится к последней полной строке входов (`issue = index[-1]`,
  `start = issue+1`) — устаревшая система никогда не называет себя текущей.

Десктопный UI подхватывает это до отправки: экран данных отдаёт `sources_through`
(даты по каждому источнику), поле месяца ограничено `max` = `fields_monthly + 1`, а при
пустом значении подставляется последний честный месяц.

## CI-скрипт и расписание

`scripts/zarr_freshness.py` переиспользует `readiness.evaluate` (те же лимиты, та же логика)
— расхождение «готовность vs скрипт» невозможно по построению. Правила приёмки:

- missing/error обязательного источника или бандла — **всегда** алерт и `exit 1`
  (в отличие от прежнего скрипта, где отсутствующий store молча пропускался);
- опциональный/поле без даты — предупреждение с явной маркировкой деградации;
- проверка идёт по production-storage из окружения (`AGROCAST_WORLD_DIR`/`AGROCAST_STATE_DIR`
  и release-манифест), то есть по тем же путям, что видит приложение;
- workflow `Свежесть zarr` (`.github/workflows/freshness.yml`) запускается еженедельно
  (cron `0 6 * * 1`); все лимиты таблицы ≥ удвоенного периода проверки (проверяется тестом
  `test_limits_are_consistent_with_update_schedule`), поэтому плановое недельное обновление
  не может само по себе вызвать алерт, а пропуск двух циклов — обязан.

## Docker / compose

- `Dockerfile HEALTHCHECK` остаётся на `/health/live` (контейнер не перезапускают из-за
  устаревших данных).
- `deploy/docker-compose.yml`: у сервиса `app` добавлен healthcheck на `/health/ready`
  (`start_period: 120s`, интервал 60s); `caddy` ждёт `app: service_healthy` — трафик не
  приходит к системе, у которой нет честных входов. У postgres-сервиса и worker ничего не
  менялось.

## Лимиты этапа

- Worker-heartbeat и задержка очереди на готовность не влияют (только информативно);
  поведенческие пороги «сколько можно ждать queued» — T13.
- Календарная политика публикаций (`available_at` с лагами источников, as-of) — T08.
- Подпись бандлов (`sha256` манифеста вместо наличия полей) — T14; контракт бандла —
  строковый `world-v1`, схема верификации артефактов не менялась.
- В веб-режиме новые forecast-запуски по-прежнему закрыты пилотными gates: readiness и gate
  подготовлены к открытию приёма, но не открывают его.
